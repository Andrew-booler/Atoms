# 问题复盘与预防

版本：1.0｜日期：2026-11-04｜适用范围：Atoms Studio 本地开发、测试与预览链路

本文复盘 2026-11-03 至 11-04 两轮交付中暴露的问题，每项按「现象 / 根因 / 为什么之前没发现 / 预防措施」记录。目的是早发现、早预防，不是追责；预防措施均为可执行动作或已落地的代码/规范约束。

## 1. 前端覆盖 `preview_url` 导致预览降级

- **现象**：Playwright 35 条全部通过，但页面实际显示「本地预览 · 沙箱未启动」；后端已启动容器并返回可访问的 `http://127.0.0.1:<port>/`。
- **根因**：构建成功后先 `setPreviewUrl(built.preview_url)`，随后 `applyDetail()` 按“刚打开项目”的语义执行 `setPreviewUrl(null)`，把预览地址清空。构建、改稿、源码编辑三处流程均受影响。
- **为什么之前没发现**：原断言只检查 iframe 内的标题，降级 `srcDoc` 同样能渲染标题，因此绿测试掩盖了功能缺失；该问题在生产同样存在。
- **预防措施**：
  1. 断言必须覆盖真实能力路径：预览用例同时断言 `preview_ready=true` 与 iframe `src` 匹配 `http://127.0.0.1:<port>/`（已写入[测试策略与规范](测试策略与规范.md)）。
  2. 禁止只用“降级分支同样成立”的结果断言；新增预览相关用例必须检查「沙箱隔离运行 · 交互可用」文案。
  3. 修复已落地：先刷新详情，再写回 `preview_url`。

## 2. 测试宿主只清库不清容器

- **现象**：连续跑多个预览用例后，从第 5 个预览开始出现 `SANDBOX_START_FAILED`；测试结束仍残留 4 个 `atoms-sandbox-*` 容器。
- **根因**：`/__test/reset` 只 TRUNCATE 数据库，容器与工作区继续存在。`SANDBOX_MAX_CONTAINERS=4` 被占满后，`_enforce_container_cap` 查不到可回收的 `executions` 记录，只能拒绝启动。
- **为什么之前没发现**：单个用例通过、全量“绿”，失败只落在日志里；容量上限是全局的，跨用例污染不会在单测中暴露。
- **预防措施**：
  1. `reset` 必须同时回收沙箱容器与 `SANDBOX_ROOT` 下的临时工作区（已写入[开发规范](开发规范.md)）。
  2. 每次跑完沙箱相关测试后手动执行 `scripts/docker-sandbox-reaper.ps1 -MaxAgeMinutes 0` 并复核为 0。
  3. 上限默认值由 4 调整为 8（`SANDBOX_MAX_CONTAINERS` 可调）；按 `user_id` 维度限额暂未实现，记为 TODO：需要按用户统计运行中容器，代价高于本轮范围。

## 3. 错误日志缺 details

- **现象**：日志只有 `沙箱不可用，artifact 已保存但预览未启动：SANDBOX_START_FAILED`，无法区分容量上限、端口冲突还是启动超时。
- **根因**：异常处理只打印 `exc.code`，丢弃了 `exc.details`。
- **为什么之前没发现**：错误码本身“看起来明确”，且失败被降级分支吞掉，没有阻塞测试。
- **预防措施**：
  1. 沙箱/AI 等外部能力失败必须记录 `code + details`（已落地）。
  2. 排查外部依赖问题时，先取 `details` 再下结论，不以错误码推断根因。

## 4. Docker 引擎半死

- **现象**：Docker Desktop UI 显示引擎 running，但 `docker info` 返回 500，`docker ps` 不可用；后端测试卡在数据库连接。
- **根因**：Docker 引擎进程已不可用，UI 状态与真实 API 不一致。
- **为什么之前没发现**：测试前没有引擎健康预检，直接进入全量执行，失败被误认为业务代码问题。
- **预防措施**：
  1. 跑测试前执行一次 `docker info`（必要时 `docker ps -a`），失败即停，不反复重试。
  2. 在测试记录中区分“环境阻塞”和“产品失败”，不用跳过结果冒充通过。

## 5. 宿主提交内存耗尽

- **现象**：高并发测试时宿主内存被耗尽，Docker 引擎随之中断，测试大面积超时。
- **根因**：多个重负载工作流并发运行（后端全量 + Playwright + Docker 构建），缺少资源约束与监控。
- **为什么之前没发现**：只看单次命令是否成功，没有观察宿主内存与 WSL2 上限。
- **预防措施**：
  1. 同一仓库同一时间只允许一个工作流执行重测试；按范围跑用例，禁止无差别全量重跑。
  2. 为 WSL2 设置内存上限与足够的页面文件，避免宿主被容器与浏览器进程拖垮。
  3. 出现引擎异常时先停手取证，不在资源紧张时重试。

## 6. 台账漏记约 3 万 tokens

- **现象**：AI 用量台账与实际调用量存在约 3 万 tokens 的缺口。
- **根因**：调用前未登记预算、调用后未立即登记，跨窗口收尾时补记遗漏。
- **为什么之前没发现**：台账与调用路径没有强绑定，缺口只能在事后对账时暴露。
- **预防措施**：
  1. 调用前先登记预算行，调用后立即登记实际用量；不允许事后凭记忆补记。
  2. 漏记只能新增“调整行”补齐并注明原因，不得改写历史行。
  3. 每次交付收尾检查台账与调用记录是否一一对应。
