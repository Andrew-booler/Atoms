# 需求说明

版本：3.2｜日期：2026-10-31｜状态：当前授权实施，验证证据独立登记

## 阅读背景与必要概念

本文面向需求阅读者和审阅者，说明 Atoms Studio 本阶段应提供什么，以及哪些行为仍只是目标。使用者在工作台提交文字，看到计划并确认执行；系统随后取得页面结构和 HTML 文档，保存后供预览与历史恢复。HTML 是浏览器呈现页面的文字格式，计划卡是展示摘要、步骤和文件说明并提供确认、调整及复制的界面区域。

项目是一次工作空间的持久记录；消息保存需求、计划和系统备注；历史版本保存一次构建的完整 HTML。记录的 id 是数据库标识，version_no 是同一项目内的版本序号；项目字段 current_version 保存当前使用的版本序号，不是历史版本的 id。例如历史记录 id 为 201、version_no 为 1 时，恢复它会把 current_version 改成 1，而不是 201。这些数字是文档示例，不是预先存在的数据。

mock 是用预置成功结果或受控失败替代外部调用；串行是前一项及其子请求全部结束后再开始下一项。本阶段要求共享账号和数据、AI 输出模拟、操作串行；当前产品不提供登录入口，Studio路由不依赖账号认证，默认使用预置输出和统一串行状态；未验证子情景不写成通过。


## 1. 产品目标和边界

Atoms Studio 是共享数据上下文中的对话式应用工作台。本阶段验证确定性流程：输入需求 → 预置模拟计划 → 确认执行 → 预置模拟结构和HTML → 保存项目、消息和版本 → 查看与恢复版本。

所有使用者共享同一账号和数据，不提供登录认证、用户管理、角色、权限或租户隔离产品模块。不考虑同时操作、并发锁和任务队列；每项操作成功或失败结束后才允许下一项。AI输出使用mock，保留未来真实AI提供者的替换边界，不评估生成工程、语义或需求满足度。

保留现有TypeScript前端和Python后端，不进行Java或其他语言迁移。本轮授权实施现有技术栈上的最小闭环，不修改生产表结构或受保护平台模块。

## 3. 操作要求

一项用户操作包括它引发的全部子请求。例如首次提交依次建项目、保存需求、取得计划；确认执行依次取得结构、取得HTML并保存。子请求逐个等待。执行中主导航、新建/选项目/删除、输入、示例提示、提交、确认/调整/复制、配置、预览操作及版本选择不可开始下一项。成功和失败均解除执行中状态。不设置自动排队、后台并发、锁或多标签协调。

浏览器强制关闭/刷新不属于可禁用的产品按钮。本阶段只要求提交成功的数据可重新读取，不承诺未提交草稿或执行中任务恢复。

## 4. 数据与模拟输出

项目、消息、版本为三种业务实体。消息role表示发言方，不是使用者权限。HTML存入版本快照，current_version指示当前序号。Studio业务路由共享读取现有记录，新记录使用非凭据标识studio-shared，不在业务请求中新增账号字段。

第一轮输入“记录饮水”，模拟提供者返回“演示计划一”、固定结构及“模拟第一版”HTML。第一轮结束后第二轮输入“增加备注”，返回第二套固定响应并在同项目追加版本。第二轮请求包含本轮requirement、plan_summary和outline，不包含历史列表或先前HTML；不要求模拟输出理解历史或保留前版业务功能。

未来真实AI只保留可替换服务接口和相同响应形状，不在本阶段实际调用或评估。

## 5. 当前规则与限制

| 事项 | 当前实现 |
|---|---|
| 重试 | 重新执行真实失败动作，闭包保留已成功阶段；未确认的建项目/存需求先经读接口核对，避免盲目重复写入 |
| 批准状态 | 构建成功与计划meta.approved/version_id同事务提交；重复构建返回已保存版本 |
| 多张计划调整 | 使用被点击卡片meta.requirement，不取最后一条需求 |
| 需求长度 | 完整保存与传递，不截断2000字符；项目名称仍限制80字符 |
| 列表容量 | 维持项目最近60条、消息最早400条，不新增分页；超容量不保证读回全部历史消息 |
| 手机入口 | 最小项目抽屉提供打开/关闭按钮，执行中禁用 |
| 错误协议 | 字段无效422、不存在404、模拟阶段/结构无效502、数据库提交失败500；复制及弹窗失败可见 |
| 版本部分成功 | 恢复成功立即同步摘要并清空旧预览；读取失败明确告知已恢复，重试仅读取 |

不提供跨标签协调和后台任务恢复。响应丢失后的核对依赖可见记录容量，超过400消息时不能承诺需求完全去重；这是既有容量限制，不增加幂等字段或服务器锁。

## 6. 验证与追溯

仅两层：单元测试对象为类或页面，所有外部调用mock；集成测试真实模块、业务接口和测试数据库协作，AI边界仍模拟。详见[测试策略](测试策略与规范.md)、[覆盖索引](测试用例与覆盖矩阵.md)及各模块文档。

范围为3业务页面、26类交互目标（原24类加手机抽屉打开/关闭）、11业务接口。自动化入口定义56个测试（单元21、集成35）；执行统计以[测试执行记录](测试执行记录.md)为准，不等于原设计所有子情景已通过。

## 7. 实施对应

前端Index协调实际业务步骤，StudioOperation集中管理busy、错误和重试；SDK接口形状保持不变。后端Studio业务路由使用既有三实体，OutputProvider协议与默认MockOutputProvider位于服务边界；RealOutputProvider只接受显式适配器，产品不创建或调用真实提供者。没有为形式创建一套控制器/仓储目录。部署与Cloud仍是占位说明。

正式技术架构见[总架构设计](总架构设计.md)，规则见[开发规范](开发规范.md)，验证见[测试执行记录](测试执行记录.md)。

## 术语表

- mock：预置成功结果或受控失败代替外部调用。
- 示例提示按钮（旧称示例芯片）：点击填入文字但不自动提交。
- 计划卡：展示计划并提供确认、调整、复制的区域。
- 抽屉：从边缘展开并可收起的面板，手机已提供项目抽屉。
- 快照：完整HTML版本记录；项目当前使用的版本序号决定显示哪个版本。
- 串行：前项成功或失败结束后才开始下一项。
- entity：具有持久身份的业务实体，本项目为项目、消息、版本。
