# 版本模块设计与测试

版本：3.1｜可读性修订日期：2026-10-31｜作者：Alex｜作者自检：已完成｜执行证据见《测试执行记录》

## 阅读背景与必要概念

本文供只初步了解工作台流程的读者阅读，不要求先阅读其他文档。Atoms Studio让使用者输入应用需求，先查看计划，点击“确认执行”后再取得界面结构和完整网页，保存到项目并预览。本阶段的目标是所有使用者共享同一账号和项目数据，操作逐项完成，AI输出由模拟提供者返回预先指定的数据（mock），不评价生成应用是否满足业务需求。当前业务路由共享读取数据、默认模拟输出；前端统一串行操作状态。验证结果与未覆盖子情景见测试执行记录。

- 项目是保存一组需求消息、计划消息和历史网页版本的容器；“当前打开的项目”指工作区正在显示的项目。
- 历史版本保存一份完整网页文本（HTML）。版本序号version_no表示同一项目的第几次成功保存；数据库记录标识id用于找到一条具体记录，两者不能互换。项目字段current_version表示项目当前使用的版本序号。
- 空闲表示上一项操作及其请求均已成功或失败结束；执行中表示这一项尚未结束。目标要求执行中不能开始另一项产品操作，不设置并发锁或队列。
- 前端是浏览器中的工作台；后端是处理请求并读写数据库的服务。HTTP接口是两者的通信约定：GET读取、POST提交、DELETE删除；200表示请求成功，201表示创建成功，404表示记录不存在或版本不属于所选项目，422表示请求字段无效，502表示输出提供者明确失败。数据库提交故障返回500，模拟结构无效返回502；错误反馈不伪造成功。
- 本文的“目标类”是后续职责设计，尚未创建。Controller是协调动作的控制器，Service是处理业务的服务，Repository是读写记录的仓储，UnitOfWork是统一提交或回滚一次数据库操作的工作单元。现有React仍使用函数组件，不能把这些目标名称当作已实现类。

## 1. 模块设计

### 1.1 适用范围

本文说明在预览区“选择版本”下拉框中恢复历史网页。恢复会改变项目当前使用的版本，不是只读浏览，也不是复制成另一个项目。

### 1.2 现有对象与目标职责

现有ArtifactPreview按version_no显示下拉选项，选择后把完整VersionSummary记录交给Index.restoreVersion；Index通过studioApi.restore提交该记录id，再调用studioApi.getVersion读取HTML。目标VersionController协调两次请求，VersionService验证版本属于项目并更新current_version，VersionRepository读取历史记录，UnitOfWork提交序号和备注，PreviewController接收读取成功的网页。

### 1.3 正常操作及请求顺序

1. 准备一个示例项目101，它有两个已保存历史版本：第1版的记录标识201保存模拟第一版，第2版标识202保存模拟第二版。项目当前使用第2版，数据库current_version=2；页面预览显示模拟第二版。201是示例记录标识，不是第201版。

2. 上一项操作结束后，使用者在预览区“选择版本”下拉框选择“v1”。组件用序号1找到对应记录，再把其数据库id=201交给恢复处理。前端给后端发送POST /api/v1/studio/projects/101/restore，请求体{version_id:201}。

3. 后端核实记录201属于项目101，将项目current_version改为这条记录的version_no=1，preview_ready设为true，追加一条kind=note的系统恢复备注并一次提交。成功返回200及项目摘要；历史两条HTML不改写，版本总数仍2。

4. 收到恢复成功后，前端才发送GET /api/v1/studio/versions/201。后端返回200及第1版详情，其中id=201、project_id=101、version_no=1、artifact_html为第一版完整网页。前端更新预览和选择器为第1版。Index立即使用恢复摘要同步页头与侧栏；后续读取失败时清空旧预览并提示部分成功。

5. 两次请求结束后，测试另发GET /api/v1/studio/projects/101，核对数据库current_version=1、历史版本总数仍2和恢复备注。整页刷新后需等初始化完成再手选项目，才能重新读取已保存网页。

6. 恢复至第1版的操作全部结束后，再提交新需求并确认，后端按已有最大序号2加一保存第3版，不覆盖第2版；项目current_version变3。

### 1.4 失败、状态和未实施项

恢复请求失败404时不继续读取版本，原current_version、历史HTML和备注保持不变。恢复成功但后续读取失败时，数据库已改为第1版，前端清除旧预览并提示已恢复但读取失败；这是部分成功，不得声称数据库未改变。恢复的两次HTTP请求不是同一事务。明确提示已恢复但读取失败，重试只读取；现有模型没有关联外键或项目内序号唯一约束声明，不能冒称已有数据库保护。

篇幅估算：按A4 210×297毫米、20毫米边距、11pt、1.5倍行距、每页约40行；从“阅读背景与必要概念”标题起到篇幅说明前，按每个非空正文行每40字符向上取整并加一行间距，标题每个计三行；Markdown标记及技术标识计入字符数。设计含上述阅读背景，不含测试数据、测试用例及术语表，约90行、2.2页；这是估算，不是实际打印页数。估算少于三页，因此设计与测试同文件维护；实际排版达到三页时需要拆分。

## 2. 模块测试

### 本文使用的示例数据与测试条件

以下数字是测试设计中的示例，不是生产库的固定记录。示例项目数据库标识为101，名称为“演示项目”。它可以按用例分别准备为“尚无历史版本”或“已经保存两个历史版本”的状态，不能同时把这两种状态混作同一前置条件。另一个项目的标识为102；999表示该次测试中不存在的记录。

已经保存两个历史版本时：第1版记录标识为201，version_no=1，网页显示“模拟第一版”；第2版记录标识为202，version_no=2，网页显示“模拟第二版”。两条版本记录都属于项目101，项目最初当前使用第2版（current_version=2），历史版本总数为2。草稿状态则current_version=0、preview_ready=false，表示尚无可预览版本。preview_ready表示是否已有可预览网页。

第一轮需求文字为“记录饮水”。固定计划对象plan包含summary（摘要“演示计划一”）、stack（技术说明数组[“HTML”]）、steps（步骤数组，title为“显示演示”、detail为“使用预置页面”）、files（文件说明数组，path为“index.html”、purpose为“固定预览”）。第二轮需求是“增加备注”，第二轮计划摘要为“演示计划二”，完整预置数据在services/studio_output.py维护。

界面结构对象outline包含title（“演示页面一”）、sections（区域数组，每项有name和blocks）、interactions（交互说明数组）及seed_data（示例数据数组）。第二轮结构标题为“演示页面二”。完整HTML由services/studio_output.py中的fixed_html提供，第一版有初始值为0的“演示计数”按钮，仅用于验证装载和刷新；两版固定数据已创建，生产默认与隔离测试共用输出契约。

请求中的requirement是需求文字；content是消息正文；role是发言方（user为使用者，assistant为助手，system为系统），不是账号权限；kind是消息类别（requirement需求、plan计划、build构建、note备注）。meta是消息附加数据，接口以对象返回、数据库以JSON文本保存。profile是提供者配置键，沿用balanced、fast、quality；本阶段目标均返回模拟输出，不调用真实模型。

plan_summary虽然名为“计划摘要”，当前前端实际发送planToText整理的文本：计划摘要、空行，以及每个步骤的编号、标题和说明。上述第一轮示例的值为“演示计划一\n\n1. 显示演示 — 使用预置页面”（\n表示换行），不是只有“演示计划一”。后文称“该轮整理后的计划文本”时均使用此规则。artifact_html是返回或保存的完整网页文本；项目详情中的current_artifact是项目当前使用版本的网页文本。

单元测试只加载一个页面或职责对象，网络、SDK（前端接口调用封装）、数据库、输出提供者、剪贴板、窗口及定时器等外部调用全部使用模拟替身，不实际请求或写库。集成测试组合实际页面、SDK、业务后端和专用测试数据库，只有AI提供者返回固定模拟结果；共享业务路由、模拟提供者及隔离数据库已建立；逐项执行证据见测试执行记录，不将设计的全部子条件视为已验证。每例独立准备数据，按顺序操作。

### 单元测试

#### 版本-单元-01：版本选择器

- 前置条件：单元隔离，分别准备0、1、2个版本，空闲和执行中状态。
- 操作步骤：无版本时查看容器；有两个版本时在下拉框选v1；执行中再次选择。
- 请求或外部替身调用：恢复和读取接口均替身，记录项目标识101、版本记录标识201；恢复成功后才记录读取调用。
- 预期响应：模拟返回恢复项目摘要和第1版详情。
- 界面结果：无版本不显示选择器；有版本按序号倒序并标当前；目标执行中不能选择。
- 持久化结果：无真实请求或写库。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 版本-单元-02：恢复请求的三种结果

- 前置条件：单元隔离，项目101当前第2版；分别设恢复成功且读取成功、恢复失败、恢复成功但读取失败。
- 操作步骤：选择v1并完成该组模拟结果。
- 请求或外部替身调用：恢复和版本读取替身；恢复失败时读取替身不得调用。
- 预期响应：各组按设定返回摘要、详情或错误。
- 界面结果：全成功显示第一版；恢复失败保留旧预览；后续读取失败显示错误而可能保留第二版。
- 持久化结果：只模拟状态；后一失败组必须说明真实集成情况下数据库已改变，不能推定未恢复。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 版本-单元-03：版本详情与摘要职责

- 前置条件：隔离Python职责对象，数据库会话全部替身；给存在201记录及不存在999两组。
- 操作步骤：读取版本并计算项目版本数量。
- 请求或外部替身调用：会话替身返回project_id=101、version_no=1、固定artifact_html及数量；不真实请求。
- 预期响应：存在组返回完整HTML和独立id/序号；不存在组404。
- 界面结果：不得把201显示成第201版。
- 持久化结果：不写真实库，不设计使用者隔离新要求；共享目标未实施。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

### 集成测试

#### 版本-集成-01：选择历史版本并恢复

- 前置条件：按本节准备项目101的两条记录201/202，current_version=2；页面空闲。
- 操作步骤：使用者在预览区选择版本下拉框选v1；两次请求结束后复查项目。
- 请求或外部替身调用：前端发送POST /api/v1/studio/projects/101/restore，请求体为{version_id:201}；成功后才发送GET /api/v1/studio/versions/201。测试在两项结束后另发GET /api/v1/studio/projects/101复查保存结果。
- 预期响应：恢复请求返回200及项目摘要，其中current_version=1；版本读取返回200及id=201、project_id=101、version_no=1和第一版artifact_html；项目复查返回200。
- 界面结果：预览与选择器变第1版。页头和侧栏立即使用恢复摘要同步，后续详情读取同步消息。
- 持久化结果：current_version从2变1；追加恢复系统备注；版本总数2，两份历史HTML不变。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 版本-集成-02：不存在版本或其他项目版本

- 前置条件：项目101当前第2版；分别准备不存在999，以及属于项目102的版本，其标识由准备结果取得。
- 操作步骤：通过实际请求能力提交两种无效恢复目标，不虚构下拉框中的不存在选项。
- 请求或外部替身调用：POST /api/v1/studio/projects/101/restore，version_id分别为999或项目102的版本记录标识；失败后不读该版本；结束后GET /api/v1/studio/projects/101复查。

#### 版本-集成-03：恢复成功但读取失败

- 前置条件：项目101有两版、当前第2版；专用环境只让后续版本读取受控失败。
- 操作步骤：选择v1，恢复结束后让读取失败；解除故障，再复查项目。
- 请求或外部替身调用：POST /api/v1/studio/projects/101/restore，{version_id:201}；成功后GET /api/v1/studio/versions/201失败；故障解除后GET /api/v1/studio/projects/101复查。
- 预期响应：恢复200及current_version=1；读取不得返回成功，故障码依受控类型记录；复查200及当前第1版网页。
- 界面结果：原浏览器预览可能仍第二版，错误必须记录为部分成功；重新读取成功才显示第一版。
- 持久化结果：数据库已恢复第1版并有备注，不能判断仍第2版；明确提示已恢复但读取失败，重试只读取。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 版本-集成-04：恢复后追加版本

- 前置条件：项目101原有两版，已成功恢复到第1版且操作结束。
- 操作步骤：输入增加备注，提交完成后确认，再复查项目。
- 请求或外部替身调用：POST /api/v1/studio/projects/101/messages，{role:"user",kind:"requirement",content:"增加备注"}；POST /api/v1/studio/projects/101/plan，{requirement:"增加备注",profile:"balanced"}；确认后POST /api/v1/studio/projects/101/outline，带本轮requirement、整理后的plan_summary、profile；成功后POST /api/v1/studio/projects/101/artifact另带本轮outline；结束后GET /api/v1/studio/projects/101。
- 预期响应：消息201，计划/结构200，网页200且version.version_no=3，复查200。
- 界面结果：显示新返回的固定网页，选择器当前第3版。
- 持久化结果：新增第3版，不覆盖原第2版；current_version=3，版本总数3；不评价新网页与旧业务的关系。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 版本-集成-05：刷新及必要字段

- 前置条件：项目101完成恢复第1版，已结束操作；字段故障组独立准备。

- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

## 3. 术语补充

- 版本记录标识：数据库id，用于定位记录；版本序号version_no仅表示项目内第几版。
- 项目当前使用的版本序号：current_version字段；恢复修改这个值，不改写历史HTML。
- 持久化：把记录提交到数据库，之后可通过实际读取接口核对，不等于仅在页面显示。
- 事务：一组数据库写入一起提交或回滚；多次HTTP请求不自动组成一个事务。
- SDK：前端业务调用封装，本项目通过它向后端发送请求。
- 目标设计：未来获批实施的职责或规则，不能据此认定当前代码已实现。

## 3. 当前实施与执行对应

本轮用户已授权实施，不设强制外部审阅。默认输出在services/studio_output.py；Index和StudioOperation串行协调SDK请求，成功/失败均释放状态。批准写计划meta；调整取所点计划需求；重试重发失败阶段；恢复摘要立即同步，部分成功明确提示并仅读取重试。项目60条、消息最早400条容量保持原状。手机新增项目抽屉打开与关闭两类控件。
