# 需求输入与配置模块设计与测试

版本：3.1｜可读性修订日期：2026-10-31｜作者：Alex｜作者自检：已完成｜执行证据见《测试执行记录》

## 阅读背景与必要概念

本文供只初步了解工作台流程的读者阅读，不要求先阅读其他文档。Atoms Studio让使用者输入应用需求，先查看计划，点击“确认执行”后再取得界面结构和完整网页，保存到项目并预览。本阶段的目标是所有使用者共享同一账号和项目数据，操作逐项完成，AI输出由模拟提供者返回预先指定的数据（mock），不评价生成应用是否满足业务需求。当前业务路由共享读取数据、默认模拟输出；前端统一串行操作状态。验证结果与未覆盖子情景见测试执行记录。

- 项目是保存一组需求消息、计划消息和历史网页版本的容器；“当前打开的项目”指工作区正在显示的项目。
- 历史版本保存一份完整网页文本（HTML）。版本序号version_no表示同一项目的第几次成功保存；数据库记录标识id用于找到一条具体记录，两者不能互换。项目字段current_version表示项目当前使用的版本序号。
- 空闲表示上一项操作及其请求均已成功或失败结束；执行中表示这一项尚未结束。目标要求执行中不能开始另一项产品操作，不设置并发锁或队列。
- 前端是浏览器中的工作台；后端是处理请求并读写数据库的服务。HTTP接口是两者的通信约定：GET读取、POST提交、DELETE删除；200表示请求成功，201表示创建成功，404表示记录不存在或版本不属于所选项目，422表示请求字段无效，502表示输出提供者明确失败。数据库提交故障返回500，模拟结构无效返回502；错误反馈不伪造成功。
- 本文的“目标类”是后续职责设计，尚未创建。Controller是协调动作的控制器，Service是处理业务的服务，Repository是读写记录的仓储，UnitOfWork是统一提交或回滚一次数据库操作的工作单元。现有React仍使用函数组件，不能把这些目标名称当作已实现类。

## 1. 模块设计

### 1.1 适用范围

本文说明输入文字、使用四个示例提示按钮、选择提供者配置和提交需求。示例提示按钮只填文字，不自动生成计划。

### 1.2 现有对象与目标职责

现有RequirementComposer显示输入框并管理焦点，Index处理提交，studioApi封装接口。目标RequirementDraft保存草稿和配置，RequirementController检查输入并发出提交意图，StudioController顺序协调服务，不让输入框直接写数据库。

### 1.3 正常操作及请求顺序

1. 前端读取GET /api/v1/studio/models，返回200及profiles/default_profile。使用者选择配置只改变浏览器内profile，无网络请求；默认沿用balanced。

2. 空对话且空闲时，使用者点击四个示例提示之一，前端将该按钮的完整文字放入输入框并使输入框获得键盘焦点，无网络请求。

3. 使用者点击“生成计划”或按Ctrl+Enter、⌘+Enter提交；普通Enter只换行。前端先去掉输入首尾空白，结果为空则不发送请求。有效提交先保存需求消息，成功后再请求计划：POST /api/v1/studio/projects/101/messages，请求体为{role:"user",kind:"requirement",content:"记录饮水"}。POST /api/v1/studio/projects/101/plan，请求体为{requirement:"记录饮水",profile:"balanced"}。

4. 首次提交没有当前项目时，先按项目模块规则创建项目，再以返回id代替上述101。目标要求执行中暂停编辑及新提交，操作结束后恢复。

### 1.4 失败、状态和未实施项

当前计划meta.requirement完整保存，确认完整传递；未知配置回退balanced。配置读取失败显示错误并允许真实重试，不假称加载成功。输入框当前最大高度168像素。

篇幅估算：按A4 210×297毫米、20毫米边距、11pt、1.5倍行距、每页约40行；从“阅读背景与必要概念”标题起到篇幅说明前，按每个非空正文行每40字符向上取整并加一行间距，标题每个计三行；Markdown标记及技术标识计入字符数。设计含上述阅读背景，不含测试数据、测试用例及术语表，约76行、1.9页；这是估算，不是实际打印页数。估算少于三页，因此设计与测试同文件维护；实际排版达到三页时需要拆分。

## 2. 模块测试

### 本文使用的示例数据与测试条件

以下数字是测试设计中的示例，不是生产库的固定记录。示例项目数据库标识为101，名称为“演示项目”。它可以按用例分别准备为“尚无历史版本”或“已经保存两个历史版本”的状态，不能同时把这两种状态混作同一前置条件。另一个项目的标识为102；999表示该次测试中不存在的记录。

已经保存两个历史版本时：第1版记录标识为201，version_no=1，网页显示“模拟第一版”；第2版记录标识为202，version_no=2，网页显示“模拟第二版”。两条版本记录都属于项目101，项目最初当前使用第2版（current_version=2），历史版本总数为2。草稿状态则current_version=0、preview_ready=false，表示尚无可预览版本。preview_ready表示是否已有可预览网页。

第一轮需求文字为“记录饮水”。固定计划对象plan包含summary（摘要“演示计划一”）、stack（技术说明数组[“HTML”]）、steps（步骤数组，title为“显示演示”、detail为“使用预置页面”）、files（文件说明数组，path为“index.html”、purpose为“固定预览”）。第二轮需求是“增加备注”，第二轮计划摘要为“演示计划二”，完整预置数据在services/studio_output.py维护。

界面结构对象outline包含title（“演示页面一”）、sections（区域数组，每项有name和blocks）、interactions（交互说明数组）及seed_data（示例数据数组）。第二轮结构标题为“演示页面二”。完整HTML由services/studio_output.py中的fixed_html提供，第一版有初始值为0的“演示计数”按钮，仅用于验证装载和刷新；两版固定数据已创建，生产默认与隔离测试共用输出契约。

请求中的requirement是需求文字；content是消息正文；role是发言方（user为使用者，assistant为助手，system为系统），不是账号权限；kind是消息类别（requirement需求、plan计划、build构建、note备注）。meta是消息附加数据，接口以对象返回、数据库以JSON文本保存。profile是提供者配置键，沿用balanced、fast、quality；本阶段目标均返回模拟输出，不调用真实模型。

plan_summary虽然名为“计划摘要”，当前前端实际发送planToText整理的文本：计划摘要、空行，以及每个步骤的编号、标题和说明。上述第一轮示例的值为“演示计划一\n\n1. 显示演示 — 使用预置页面”（\n表示换行），不是只有“演示计划一”。后文称“该轮整理后的计划文本”时均使用此规则。artifact_html是返回或保存的完整网页文本；项目详情中的current_artifact是项目当前使用版本的网页文本。

单元测试只加载一个页面或职责对象，网络、SDK（前端接口调用封装）、数据库、输出提供者、剪贴板、窗口及定时器等外部调用全部使用模拟替身，不实际请求或写库。集成测试组合实际页面、SDK、业务后端和专用测试数据库，只有AI提供者返回固定模拟结果；共享业务路由、模拟提供者及隔离数据库已建立；逐项执行证据见测试执行记录，不将设计的全部子条件视为已验证。每例独立准备数据，按顺序操作。

### 单元测试

#### 输入-单元-01：输入与提交

- 前置条件：单元隔离；分别输入空白、单字、多行。
- 操作步骤：分别点击生成计划、按Ctrl/⌘+Enter、按普通Enter；另组设执行中。
- 请求或外部替身调用：提交回调使用替身；有效按钮或快捷键各触发一次，空白和普通Enter不触发。
- 预期响应：回调记录去除首尾空白后的文字。
- 界面结果：普通Enter换行；目标执行中不能编辑或提交，结束后恢复。
- 持久化结果：无真实保存。
- 依据与状态：当前输入规则与新串行目标，生成计划期间禁止编辑；未执行。

#### 输入-单元-02：全部示例提示

- 前置条件：单元隔离，空对话且空闲；另组有消息或执行中。
- 操作步骤：逐个点击四个提示按钮。
- 请求或外部替身调用：焦点能力与协作对象使用替身；不调用提交接口。
- 预期响应：每次只接收对应提示全文。
- 界面结果：填入文字并聚焦，不自动提交；按出现条件检查隐藏或不可操作。
- 持久化结果：无保存。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 输入-单元-03：配置与输入高度

- 前置条件：模拟正常配置、空配置、失败配置；准备长中文、emoji表情及多行。
- 操作步骤：逐项选择balanced、fast、quality并编辑长文字。
- 请求或外部替身调用：配置读取、尺寸及焦点依赖全部替身。
- 预期响应：正常组返回配置；空和失败组按预置结果。
- 界面结果：默认balanced，空清单禁用选择；失败现状无显式错误；高度最大168像素，可滚动且无乱码。
- 持久化结果：无真实保存。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 输入-集成-03：配置传递或读取失败

#### 输入-集成-04：空白与长输入

- 前置条件：项目101空闲；逐组准备空白、多行中文与emoji，以及1999、2000、2001、10000字符输入。

## 3. 术语补充

- 版本记录标识：数据库id，用于定位记录；版本序号version_no仅表示项目内第几版。
- 项目当前使用的版本序号：current_version字段；恢复修改这个值，不改写历史HTML。
- 持久化：把记录提交到数据库，之后可通过实际读取接口核对，不等于仅在页面显示。
- 事务：一组数据库写入一起提交或回滚；多次HTTP请求不自动组成一个事务。
- SDK：前端业务调用封装，本项目通过它向后端发送请求。
- 目标设计：未来获批实施的职责或规则，不能据此认定当前代码已实现。

## 3. 当前实施与执行对应

本轮用户已授权实施，不设强制外部审阅。默认输出在services/studio_output.py；Index和StudioOperation串行协调SDK请求，成功/失败均释放状态。批准写计划meta；调整取所点计划需求；重试重发失败阶段；恢复摘要立即同步，部分成功明确提示并仅读取重试。项目60条、消息最早400条容量保持原状。手机新增项目抽屉打开与关闭两类控件。

上文七项式用例保留设计追溯，其中历史“未执行”只表示原文档阶段；本轮实际运行脚本与子情景差异以[测试执行记录](../测试执行记录.md)为准。自动化同编号的标题和断言并不覆盖原设计每个子条件，不能仅由标题数量推导全部设计通过。
