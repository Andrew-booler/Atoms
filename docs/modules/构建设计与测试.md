# 模拟构建、消息与串行操作模块设计与测试

版本：3.1｜可读性修订日期：2026-10-31｜作者：Alex｜作者自检：已完成｜执行证据见《测试执行记录》

## 阅读背景与必要概念

本文供只初步了解工作台流程的读者阅读，不要求先阅读其他文档。Atoms Studio让使用者输入应用需求，先查看计划，点击“确认执行”后再取得界面结构和完整网页，保存到项目并预览。本阶段的目标是所有使用者共享同一账号和项目数据，操作逐项完成，AI输出由模拟提供者返回预先指定的数据（mock），不评价生成应用是否满足业务需求。当前业务路由共享读取数据、默认模拟输出；前端统一串行操作状态。验证结果与未覆盖子情景见测试执行记录。

- 项目是保存一组需求消息、计划消息和历史网页版本的容器；“当前打开的项目”指工作区正在显示的项目。
- 历史版本保存一份完整网页文本（HTML）。版本序号version_no表示同一项目的第几次成功保存；数据库记录标识id用于找到一条具体记录，两者不能互换。项目字段current_version表示项目当前使用的版本序号。
- 空闲表示上一项操作及其请求均已成功或失败结束；执行中表示这一项尚未结束。目标要求执行中不能开始另一项产品操作，不设置并发锁或队列。
- 前端是浏览器中的工作台；后端是处理请求并读写数据库的服务。HTTP接口是两者的通信约定：GET读取、POST提交、DELETE删除；200表示请求成功，201表示创建成功，404表示记录不存在或版本不属于所选项目，422表示请求字段无效，502表示输出提供者明确失败。数据库提交故障返回500，模拟结构无效返回502；错误反馈不伪造成功。
- 本文的“目标类”是后续职责设计，尚未创建。Controller是协调动作的控制器，Service是处理业务的服务，Repository是读写记录的仓储，UnitOfWork是统一提交或回滚一次数据库操作的工作单元。现有React仍使用函数组件，不能把这些目标名称当作已实现类。

## 1. 模块设计

### 1.1 适用范围

本文说明需求、计划、界面结构、网页如何依次传递，并在成功时保存版本。构建在这里指取得完整HTML并写入数据库，不是发布网站，也不检查模拟网页的生成质量。

### 1.2 现有对象与目标职责

现有Index编排请求，studio路由处理写入，studio_ai提供输出。目标StudioController统一空闲/执行中状态，BuildController顺序调用阶段，BuildService协调保存；OutputProvider是输出接口，MockOutputProvider返回预置数据，未来RealOutputProvider可替换。三个Repository分别读写项目、消息、版本，UnitOfWork使网页阶段三项写入一起成功或一起回滚。

### 1.3 正常操作及请求顺序

1. 项目101无版本且空闲时，使用者提交记录饮水。前端先保存需求，再请求固定计划：POST /api/v1/studio/projects/101/messages，请求体为{role:"user",kind:"requirement",content:"记录饮水"}。POST /api/v1/studio/projects/101/plan，请求体为{requirement:"记录饮水",profile:"balanced"}。需求返回201，计划返回200后结束本次提交，等待使用者确认。

2. 使用者点击确认执行，前端先请求界面结构，成功后才请求网页：POST /api/v1/studio/projects/101/outline，请求体包含requirement:"记录饮水"、plan_summary:该轮整理后的计划文本、profile:"balanced"。POST /api/v1/studio/projects/101/artifact，请求体包含requirement:"记录饮水"、plan_summary:同一轮整理后的计划文本、outline:刚返回的界面结构对象、profile:"balanced"。界面结构请求返回200及outline/model；网页保存请求返回200及project（项目摘要）、version（版本摘要）、message（构建消息）、outline_title（结构标题）、artifact_html（完整网页）。

3. 后端网页阶段为项目追加一条完整HTML版本和一条构建消息，并把current_version改为新版本序号、preview_ready设为true。这三项一次提交。前端成功收到响应后更新预览，整项操作结束才允许下一项。

4. 第一轮全部结束后，使用者在同一个项目输入增加备注，再提交和确认。各请求仍只传本轮需求、整理后的计划文本、配置和结构，不传历史消息列表或第一版HTML；第二版追加保存，第一版文本不改写。

### 1.4 失败、状态和未实施项

阶段失败就结束操作，不继续下游请求，保留已存在的预览。网页提交故障回滚本次版本、构建消息和当前序号更新，但不抹去更早请求已经保存的需求或计划。当前重试重新执行失败动作，成功阶段保留；消息详情按id升序只取最早400条。统一串行状态及默认mock已接入。

篇幅估算：按A4 210×297毫米、20毫米边距、11pt、1.5倍行距、每页约40行；从“阅读背景与必要概念”标题起到篇幅说明前，按每个非空正文行每40字符向上取整并加一行间距，标题每个计三行；Markdown标记及技术标识计入字符数。设计含上述阅读背景，不含测试数据、测试用例及术语表，约87行、2.2页；这是估算，不是实际打印页数。估算少于三页，因此设计与测试同文件维护；实际排版达到三页时需要拆分。

## 2. 模块测试

### 本文使用的示例数据与测试条件

以下数字是测试设计中的示例，不是生产库的固定记录。示例项目数据库标识为101，名称为“演示项目”。它可以按用例分别准备为“尚无历史版本”或“已经保存两个历史版本”的状态，不能同时把这两种状态混作同一前置条件。另一个项目的标识为102；999表示该次测试中不存在的记录。

已经保存两个历史版本时：第1版记录标识为201，version_no=1，网页显示“模拟第一版”；第2版记录标识为202，version_no=2，网页显示“模拟第二版”。两条版本记录都属于项目101，项目最初当前使用第2版（current_version=2），历史版本总数为2。草稿状态则current_version=0、preview_ready=false，表示尚无可预览版本。preview_ready表示是否已有可预览网页。

第一轮需求文字为“记录饮水”。固定计划对象plan包含summary（摘要“演示计划一”）、stack（技术说明数组[“HTML”]）、steps（步骤数组，title为“显示演示”、detail为“使用预置页面”）、files（文件说明数组，path为“index.html”、purpose为“固定预览”）。第二轮需求是“增加备注”，第二轮计划摘要为“演示计划二”，完整预置数据在services/studio_output.py维护。

界面结构对象outline包含title（“演示页面一”）、sections（区域数组，每项有name和blocks）、interactions（交互说明数组）及seed_data（示例数据数组）。第二轮结构标题为“演示页面二”。完整HTML由services/studio_output.py中的fixed_html提供，第一版有初始值为0的“演示计数”按钮，仅用于验证装载和刷新；两版固定数据已创建，生产默认与隔离测试共用输出契约。

请求中的requirement是需求文字；content是消息正文；role是发言方（user为使用者，assistant为助手，system为系统），不是账号权限；kind是消息类别（requirement需求、plan计划、build构建、note备注）。meta是消息附加数据，接口以对象返回、数据库以JSON文本保存。profile是提供者配置键，沿用balanced、fast、quality；本阶段目标均返回模拟输出，不调用真实模型。

plan_summary虽然名为“计划摘要”，当前前端实际发送planToText整理的文本：计划摘要、空行，以及每个步骤的编号、标题和说明。上述第一轮示例的值为“演示计划一\n\n1. 显示演示 — 使用预置页面”（\n表示换行），不是只有“演示计划一”。后文称“该轮整理后的计划文本”时均使用此规则。artifact_html是返回或保存的完整网页文本；项目详情中的current_artifact是项目当前使用版本的网页文本。

单元测试只加载一个页面或职责对象，网络、SDK（前端接口调用封装）、数据库、输出提供者、剪贴板、窗口及定时器等外部调用全部使用模拟替身，不实际请求或写库。集成测试组合实际页面、SDK、业务后端和专用测试数据库，只有AI提供者返回固定模拟结果；共享业务路由、模拟提供者及隔离数据库已建立；逐项执行证据见测试执行记录，不将设计的全部子条件视为已验证。每例独立准备数据，按顺序操作。

### 单元测试

#### 构建-单元-01：阶段编排

- 前置条件：单元隔离，固定计划；分别设界面结构延迟成功、网页成功或各阶段失败。
- 操作步骤：点击确认并逐步完成模拟结果。
- 请求或外部替身调用：结构和网页调用替身；结构完成成功后才调用网页，结构失败不调用网页。
- 预期响应：返回固定结构及HTML或受控错误。
- 界面结果：进度说明对应实际等待阶段，不提前完成；失败保留旧预览并结束操作。
- 持久化结果：无真实写入。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 构建-单元-02：消息与错误显示

- 前置条件：单元隔离，准备需求、计划、构建、备注和错误提示，并给损坏meta、非法时间值。
- 操作步骤：查看消息与时间，点击重试。
- 请求或外部替身调用：接口、滚动和时钟全部替身；重试不调用生成接口。
- 预期响应：没有重发响应。
- 界面结果：错误清除；时间不显示NaN（无效数字）；当前构建消息最多显示4项interactions交互说明。
- 持久化结果：不新增消息或版本；重试重新调用失败动作；已成功写入不重复。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 构建-单元-03：网页保存职责

- 前置条件：隔离Python路由职责，数据库、提供者和时钟全部替身。
- 操作步骤：分别模拟网页成功及数据库提交失败。
- 请求或外部替身调用：generate_artifact输出替身返回固定HTML；数据库会话替身记录版本、消息、当前序号更新及commit提交，失败记录rollback回滚。
- 预期响应：成功返回同一HTML及版本信息；失败不返回成功。
- 界面结果：不把失败当作成功版本。
- 持久化结果：只检查替身调用，不写实际数据库；不评价HTML业务质量。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

- 前置条件：每组独立准备消息失败或计划、结构、网页提供者明确失败。
- 操作步骤：提交或确认对应阶段，失败结束后再测试下一组，最后点重试。
- 请求或外部替身调用：保存需求POST /api/v1/studio/projects/101/messages失败则不发计划；计划POST /api/v1/studio/projects/101/plan使用本轮requirement/profile；结构POST /api/v1/studio/projects/101/outline另带整理后的plan_summary；网页POST /api/v1/studio/projects/101/artifact另带刚返回outline。结构失败不请求网页；重试无网络请求。

- 界面结果：错误可见、操作结束，旧HTML保留，不显示失败阶段已成功。
- 持久化结果：不新增成功版本或构建消息；先前已提交需求或计划可以仍存在。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 构建-集成-04：网页提交故障及消息容量

- 前置条件：固定提供者成功，数据库只在网页提交时注入故障；容量另用399、400、401条消息独立数据组。
- 操作步骤：确认构建，失败结束后复查；各容量组读取项目。
- 请求或外部替身调用：POST /api/v1/studio/projects/101/artifact，请求体包含requirement:"记录饮水"、plan_summary:同一轮整理后的计划文本、outline:刚返回的界面结构对象、profile:"balanced"。失败后GET /api/v1/studio/projects/101；容量组各GET /api/v1/studio/projects/101。
- 预期响应：提交故障不返回成功，返回500；复查详情200。
- 界面结果：失败不显示新版本；401条时最后一条可能不在最早400条中。
- 持久化结果：没有孤立新版本、成功构建消息或新current_version；消息维持最近60项目与最早400消息，不新增分页。
- 依据与状态：当前实现与设计；执行结果及子情景差异见测试执行记录。

#### 构建-集成-05：执行中禁止下一项

- 前置条件：分别对初始化、项目读取、计划、构建、删除、恢复注入延迟；每组只开始一项。
- 操作步骤：等待期间逐个尝试所有出现的24类交互目标，完成或失败结束后再操作。
- 请求或外部替身调用：等待期间不得新增业务请求，也不得调用剪贴板或外开窗口；当前操作内部既定请求仍顺序继续。结束后新操作才能发对应完整接口。
- 预期响应：原操作按组成功或失败结束；被禁止动作没有新响应。
- 界面结果：不能导航、切项目、编辑、提交、复制、选配置或版本、刷新、外开、切视图；结束后恢复。
- 持久化结果：被禁止动作不写数据库。不建立同时成功的并发用例或锁方案。
- 依据与状态：全入口串行是目标；现有初始化可能并行，部分控件尚可操作；未执行。

## 3. 术语补充

- 版本记录标识：数据库id，用于定位记录；版本序号version_no仅表示项目内第几版。
- 项目当前使用的版本序号：current_version字段；恢复修改这个值，不改写历史HTML。
- 持久化：把记录提交到数据库，之后可通过实际读取接口核对，不等于仅在页面显示。
- 事务：一组数据库写入一起提交或回滚；多次HTTP请求不自动组成一个事务。
- SDK：前端业务调用封装，本项目通过它向后端发送请求。
- 目标设计：未来获批实施的职责或规则，不能据此认定当前代码已实现。

## 3. 当前实施与执行对应

本轮用户已授权实施，不设强制外部审阅。默认输出在services/studio_output.py；Index和StudioOperation串行协调SDK请求，成功/失败均释放状态。批准写计划meta；调整取所点计划需求；重试重发失败阶段；恢复摘要立即同步，部分成功明确提示并仅读取重试。项目60条、消息最早400条容量保持原状。手机新增项目抽屉打开与关闭两类控件。

上文七项式用例保留设计追溯，其中历史“未执行”只表示原文档阶段；本轮实际运行脚本与子情景差异以[测试执行记录](../测试执行记录.md)为准。自动化同编号的标题和断言并不覆盖原设计每个子条件，不能仅由标题数量推导全部设计通过。
